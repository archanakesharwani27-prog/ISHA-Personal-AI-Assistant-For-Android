# AURA 2.0 — MASTER ENGINEERING SPECIFICATION

## 0. Product Definition

**AURA = Autonomous Universal Real-time Assistant**

AURA ka target ek normal chatbot ya fixed-command automation bot nahi hai.

AURA should behave as:

> **Personal conversational AI + realtime multimodal assistant + Android operator + planning agent + memory system + adaptive execution engine**

AURA ko user ke arbitrary natural-language requests samajhne chahiye, task ko break karna chahiye, available capabilities discover karni chahiye, actions execute karne chahiye, actual result verify karna chahiye, failure se strategy learn karni chahiye, aur future tasks me improved strategy use karni chahiye.

### Existing source baseline

Tumhare current dossier ke mutabik AURA already has:

* Jetpack Compose UI
* `AuraAssistantViewModel`
* `GeminiLiveClient`
* `GeminiChatService`
* `AuraMemoryManager`
* `JarvisToolRegistry`
* Accessibility automation
* Notification Listener
* OpenWakeWord-based `WakeWordService`
* Camera/live screen controls concept
* 52 native tools
* persistent memory
* ChatGPT-inspired UI/voice surface

AURA 2.0 ka kaam in pieces ko replace karna nahi, balki unke beech **strong orchestration and execution system** establish karna hai.

# 5. Audio Architecture

## Mic ownership rule

A single microphone owner should exist at any moment.

```text
WAKE MODE
WakeWordService
      ↓
mic owner = WakeWordService

wake detected
      ↓
stop/suspend wake capture
      ↓
LIVE MODE
GeminiLiveSession
      ↓
mic owner = AudioCapture
      ↓
session finished
      ↓
release
      ↓
wake service resumes
```

Never allow:

```text
WakeWordService + GeminiLiveClient
                ↓
        simultaneous AudioRecord
```

because this is a common source of unreliable capture.

## Audio pipeline

```text
Microphone
   ↓
AudioRecord
   ↓
PCM 16-bit mono 16kHz
   ↓
VAD
   ↓
AEC / AGC
   ↓
Chunker
   ↓
Gemini Live
```

Current Gemini Live documentation supports raw 16-bit PCM mono audio at 16 kHz for input, while Live audio output is 24 kHz in the examples.

Current AURA dossier also defines 16 kHz input and 24 kHz AudioTrack output.

# 7. Barge-In Architecture

Current dossier already intends barge-in behavior.

AURA 2.0:

```text
AURA SPEAKING
     ↓
Audio playback active
     ↓
VAD monitors user speech
     ↓
Speech confidence > threshold
     ↓
interrupt token
     ↓
AudioTrack.flush()
     ↓
cancel current response generation
     ↓
mark current turn INTERRUPTED
     ↓
capture user's full sentence
     ↓
new reasoning turn
```

Important distinction:

### Interruption types

**Attention interruption**

> “Ruko, meri baat sun rahi ho?”

Response:

> “Hmm, haan. Aap bolo.”

**Replacement command**

> “Ruko, Wi-Fi band nahi, Bluetooth on karo.”

Old task cancel/revise.

**Additional instruction**

> “Aur brightness bhi kam kar do.”

Existing plan me new step add.

**Conversational overlap**

User simply speaks while AURA is talking.

AURA stops speaking and listens.

# 9. Gemini Live Tool Loop

Gemini Live supports function calling, but the client is responsible for executing the requested function and sending the tool response back.

Correct pipeline:

```text
Gemini Live
    ↓
toolCall
    ↓
ToolCallParser
    ↓
ToolRegistry lookup
    ↓
ToolValidator
    ↓
PolicyEngine
    ↓
ExecutionEngine
    ↓
Verification
    ↓
ToolResult
    ↓
Gemini Live tool response
    ↓
Natural language response
```

Do not implement:

```text
toolCall
 ↓
execute
 ↓
"ok"
```

unless actual execution result says `ok`.

# 17. Accessibility Layer

Your dossier currently assigns Accessibility to WhatsApp automation, UI interaction, settings automation, and other hands-free actions.

AURA 2.0 should use it as a **fallback capability**, not as the first choice for every operation.

Android officially manages accessibility services through system lifecycle and explicit user enablement; Android documentation also states accessibility services are intended to assist users with disabilities.

Therefore:

```text
Native API available?
       ↓ yes
Use native
       ↓ no
Intent/API?
       ↓ yes
Use that
       ↓ no
Accessibility available?
       ↓ yes
Use supported UI automation
       ↓ no
User handoff
```

# 18. Vision Pipeline

AURA needs two distinct visual inputs:

## A. User photo/camera

```text
Camera
 ↓
JPEG/WebP
 ↓
VisionContext
 ↓
Gemini
 ↓
analysis / action
```

Example:

> “AURA, is photo me kya problem hai?”

## B. Live screen

```text
MediaProjection
 ↓
FrameSampler
 ↓
Change Detection
 ↓
Compression
 ↓
Realtime session
 ↓
Gemini
```

Android's current MediaProjection foreground-service model has explicit permission and foreground-service requirements, particularly on newer Android versions.

AURA should therefore implement screen sharing as:

```text
USER INITIATES SHARE
        ↓
request MediaProjection consent
        ↓
start allowed service
        ↓
capture frames
        ↓
send selected frames
```

Not as an invisible perpetual capture mechanism.

# 27. Background Architecture

Background mode must be designed around Android's actual lifecycle rules.

Android restricts background foreground-service starts on newer versions, and microphone/camera foreground services have additional while-in-use requirements. Android 14+ also requires explicit foreground-service types and corresponding permissions.

Therefore AURA should separate:

```text
ALWAYS-ON CAPABILITIES

Wake detector
Routine scheduler
```
